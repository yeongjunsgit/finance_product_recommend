## 3. 정제 목표: 원문을 덮어쓰지 않고 분류와 조건을 추가

AI로 모든 데이터를 다시 작성하는 것보다, 문장 필드에서 비교에 필요한 조건을 추출하는 방식이 적합하다. 이 문서의 데이터 구조와 운영 방식은 설계 제안이다.

| 실제 첨부 원문 일부 | 보존해야 할 구분 |
|---|---|
| ‘최초가입 우대 : 0.1%’ | 은행 첫 거래인지 해당 상품 첫 가입인지 문장만으로 확정하지 않음. 같은 항목의 ‘단위는 연%p’ 근거도 함께 연결 |
| ‘신규고객 우대금리 : 연 0.1%p’ | 신규고객의 정의가 없으면 범위 미확인 |
| ‘가입일 기준 과거 1년간 당행 정기예금 신규이력이 없는 고객 0.10%’ | 은행 정기예금 신규 이력, 과거 1년, 가입일 기준이라는 조건을 모두 유지 |
| ‘신용/체크카드 보유’ | 카드 보유 조건. 카드 사용 실적과 구분 |
| ‘급여통장 보유’ | 통장 보유 조건. 급여이체 실적과 구분 |
| ‘최고 연 0.2%p’ 및 여러 항목 | 개별 항목을 합산해 상한을 넘기지 않음. 중복불가·OR·AND·그룹 한도 유지 |

상위 분류는 고객 이력, 급여, 카드, 자동이체, 비대면 가입, 보유 상품 등으로 정리한다. 세부 필드에는 적용 범위, 조건·단위·금액·횟수·기간, 판단 시점, 우대 폭, 중복 관계·상한, 원문 근거, 미확인 사항·검토 상태를 둔다. 표시용 짧은 요약과 필터·계산용 구조를 구분한다.

첨부에는 `spcl_cnd` 안에 분할 인출 안내나 고객별 가입 한도가 들어 있는 상품도 있고, 문장이 중간에 끝난 예시도 있다. 따라서 필드명만 믿어 모든 내용을 ‘우대’로 강제 분류하지 않는다. ‘없음/해당없음’, null, 외부 홈페이지 참조, 해석 불가를 서로 다른 상태로 보존한다. 숫자 오타처럼 보이는 값도 근거 없이 고치지 않는다.

AI 결과가 정해진 JSON 모양으로 나오도록 제한할 수 있지만, 형식이 맞아도 의미가 틀릴 수 있다. [Structured Outputs 공식 문서](https://developers.openai.com/api/docs/guides/structured-outputs)도 내용 오류 가능성을 명시한다. 원문 구절 존재 여부·수치 근거·단위·논리 그룹을 서버가 검증하고, 복잡한 수식·외부 참조·모호한 조건은 검토 대상으로 둔다. AI의 자체 확신 점수만으로 자동 승인하지 않는다. 검증 전 결과를 사용자 자격 판정이나 우대 확정 계산에 바로 사용하지 않는다.

## 4. 매일 09:00 수집 시 권장 처리

1. Asia/Seoul 기준 09:00에 필요한 권역·페이지·기간의 원문을 수집한다. 시작 시각과 사용자 공개 완료 시각은 별도다.
2. 코드·날짜·금리·기간·null·구분자·반복 문자열은 서버 규칙으로 변환한다. 원문과 수집 상태는 보존한다.
3. 정제 대상 문장 및 그 해석에 필요한 은행·상품군·참조 맥락을 묶어 해시를 계산한다. 전체 JSON 해시만 쓰면 금리·공시일 변경 때문에 불필요한 AI 호출이 발생한다.
4. 같은 은행·상품군·필요 맥락·문장·정제 버전이면 이전 검증 결과를 재사용한다. 같은 문구라도 다른 은행의 구체 자격을 동일하다고 병합하지 않는다. 범용 분류 사전의 재사용과 상품 조건의 재사용을 구분한다.
5. 신규·변경·이전 검토 실패·정제 버전 변경 항목만 AI에 전달한다. 서로 독립된 약 10개 항목을 한 요청으로 묶는 방식을 출발점으로 삼되, 실제 토큰 길이와 출력 한도로 나눈다. 한 항목의 논리 조건을 임의로 잘라 중복불가·상한을 잃지 않도록 한다.
6. 스키마·근거 검증 후 현재 원문 해시와 맞는 정제본을 공개한다. 검토 중인 상품은 원문과 미확인 상태를 보여주거나 정제 기반 판정에서 제외한다. 바뀐 원문에 과거 정제본을 조용히 붙이지 않는다.
7. 수집 실패와 미등재를 구분한다. 금리만 바뀌고 정제 입력·참조 맥락이 같다면 문장 AI 호출을 생략할 수 있지만, 금액·이자 계산과 유효성 검증은 새 수치로 갱신한다.
8. 실제 입력·출력·추론 토큰, 요청·재시도 수, 검토 비용, 변경률, 완료 시각을 기록한다.

## 5. 7개 상품군 예산 시나리오

실제 7개 전체 데이터나 다일 수집본은 없다. 다음은 **각 상품군의 규모와 문장 길이가 첨부 예금과 같을 때만** 적용하는 가상 예산이다. 실측 결과를 7개 상품군의 확정 사용량으로 제시하지 않는다.

- 전체 JSON 입력만 단순 7배: 하루 229,803토큰, 30일 6,894,090토큰. 지침·출력은 별도다.
- 5개 문장 필드와 ID 입력만 7배: 하루 91,693토큰. 숫자·옵션을 AI에 보내지 않는 차이다.
- 은행 맥락을 넣고 완전히 같은 문장 묶음을 중복 제거하면 이 예시에서 74개 묶음이다. 10개씩 묶어 보내는 짧은 지침은 요청당 실측 220토큰이다. 이 문서의 시나리오는 총 518개 묶음(74 × 7), 정제 결과는 묶음당 500~1,200 출력 토큰이라고 가정했다. 이는 넓은 문장 필드 구조화 예산이며 우대 태그만 추출하는 출력보다 길 수 있다.

| AI 재처리 비율 가정 | 일 처리 묶음 | 일 입력 예산 | 일 출력 예산 | 일 합계 | 30일 합계 |
|---|---:|---:|---:|---:|---:|
| 최초 전체 / 매일 100% 재처리 | 518 | 103,735 | 259,000~621,600 | 362,735~725,335 | 10,882,050~21,760,050 |
| 매일 10% | 52 | 10,586 | 26,000~62,400 | 36,586~72,986 | 1,097,580~2,189,580 |
| 매일 5% | 26 | 5,293 | 13,000~31,200 | 18,293~36,493 | 548,790~1,094,790 |
| 매일 1% | 6 | 1,290 | 3,000~7,200 | 4,290~8,490 | 128,700~254,700 |
| 변경 없음(정제 입력·버전도 동일) | 0 | 0 | 0 | 0 | 0 |

전체 행은 최초 1회 비용으로도 해석할 수 있다. 변경률별 30일 합계는 초기 적재 이후 매일 같은 비율이 바뀐다는 가정이며 첫 전체 처리비는 별도다. 실제 출력은 아직 생성하지 않았으므로 비용 절감·품질·처리 시간을 보장하는 수치는 아니다. API 메시지 포장·정식 JSON 스키마·추론·재시도·추가 검토 모델은 위 표에 미포함이다. 긴 구조화 출력이 단순 원문 재작성보다 클 수 있어 입력 절감만으로 전체 비용 절감률을 계산하면 안 된다.

모델·제공자가 달라도 계산식은 다음과 같다.

`일 비용 = 입력 토큰 / 1,000,000 × 입력 단가 + 과금 출력 토큰 / 1,000,000 × 출력 단가`

출력에 과금되는 추론 토큰이 있는 모델이면 화면에 보이는 JSON 길이만으로 과금 출력을 추정하지 않는다.

### 금액 환산 예시

2026-11-24 확인한 [GPT-6 Luna 공식 모델 페이지](https://developers.openai.com/api/docs/models/gpt-6-luna)의 Standard 단가는 100만 입력 토큰당 USD 0.10, 출력당 USD 0.50이다. 이는 계산용 가격 예시이며 이 작업에서 해당 모델의 정제 정확도를 검증하거나 채택한 것은 아니다. 로컬 측정은 o200k_base 기준이므로 실제 선택 모델의 입력 계산·usage와 대조해야 한다.

위 가정으로 최초 전체 처리 1회는 약 USD 0.14~0.32, 매일 전체 재처리는 30일 약 USD 4.20~9.64, 일일 5% 변경분만 재처리는 30일 약 USD 0.21~0.48이다. API 부가 토큰·추론·재시도·검토, 환율·세금·서버 비용은 제외했다. 작은 모델의 오류 때문에 검토·재시도가 늘면 가격만으로 예상한 절감이 나오지 않을 수 있다.

[Batch API 공식 안내](https://developers.openai.com/api/docs/guides/batch)는 동기 API 대비 50% 할인과 최대 24시간 완료 창을 설명한다. 09:00에 작업을 시작해 바로 공개해야 하는 요구와는 맞지 않을 수 있다. 10개 문장을 한 요청으로 묶는 것과 Batch API는 서로 다른 최적화다. 이 표는 Batch 할인이나 프롬프트 캐시 할인을 적용하지 않았다.

## 6. 다음 확인

- 7개 상품군의 인증 실응답을 권역·페이지·기간별로 전부 수집해 위 스크립트로 다시 측정한다. 연금저축의 실제 사용 엔드포인트와 분기·보험 포함 범위를 먼저 확정한다.
- 7~14일 정도 문장 해시 변경률을 관찰한다. 모든 상품이 매일 같은 비율로 바뀐다고 가정하지 않는다.
- 최초가입·은행 신규·휴면 복귀, 카드 보유·실적, AND/OR·상한·단위·참조 누락을 포함한 검토용 사례를 만들고 원문 근거·조건 누락·수치 오류를 평가한다.
- 작은 모델의 분류·조건 추출과 검토 대상 분리부터 검증한 뒤, 실제 usage를 이용해 일일 예산과 중단·보류 기준을 정한다. 학습이나 파인튜닝은 초기 정제의 전제조건이 아니다.
