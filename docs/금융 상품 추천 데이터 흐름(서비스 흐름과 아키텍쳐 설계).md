# 금융 상품 추천 데이터 흐름 (서비스 흐름과 아키텍쳐 설계)

# 1. 서비스 흐름

> 사용자가 우리의 서비스를 이용할 때의 그 시나리오를 가정해보고 어떤 흐름으로 고객이 원하는 결과를 얻어낼 수 있을지 생각해보는 방식이다.
>
> 이렇게 하면 사용자의 목적을 파악할 수 있고, 그 목적을 이루기 위해서 어떤 기능들이 필요할지 분석해볼 수 있다.

## 1) 서비스 흐름 시나리오 방식

```
사용자 상황과 목표
- 나는 ______해서 ______하고 싶다.

정상 흐름
1. 사용자가 ______한다.
2. 서비스가 ______한다.
3. 사용자가 ______한다.
4. 서비스가 ______한다.

비교가 끝났다고 볼 수 있는 순간
- 사용자가 ______할 수 있다.

예외 한 가지
- 확인한 조건에 맞는 상품이 0개라면 서비스는 ______하고,
  사용자는 다음으로 ______할 수 있다.
```

- 시나리오는 서비스를 크게 관통하는 경우 1개와 발생할 것 같은 예외 사항들을 몇가지 만들어서 그 예외사항을 어떻게 처리할 것인가를 마인드 맵처럼 꼬리를 물고 제시되면 된다.

  - 대표 흐름에서 검토해야할 것을 한번 알아보자

    1. 생각하는 서비스를 사용자가 어떠한 목적을 가지고 방문한 것 부터 사용자가 원하는 결과를 얻을 때까지의 흐름을 생각해야한다.

    2. 흐름에서 발생하는 각 상황들에 어떠한 기능이 이를 수행하는지 생각한다.

       - 사용자가 원하는 목적을 AI에게 이야기 한다. 

         - AI에게 질문을 할 수 있는 입력창이 필요하다.

       - 서비스가 사용자의 요청을 기반으로 상품을 출력한다.  

         1. AI가 사용자의 입력을 해석하고 상품 필터링에 필요한 정보들을 파악한다.
         2. 추려낸 정보를 토대로 가지고 있는 상품 데이터를 필터링 한다. (이를 위해 먼저 상품이 DB에 저장되어 있어야한다.)
         3. 백엔드에서 제공한 데이터를 화면에 출력한다.

       - 사용자가 제시된 상품들을 눌러보며 상세 정보를 확인한다.

         1. 각 상품을 클릭할 수 있는 요소로 만들고, 클릭 시 상세한 정보를 확인할 수 있도록 만든다.

       - 사용자가 상세 정보에서 해당 상품을 가입할 수 있는 채널로 이동한다.

         - 가입할 수 있는 채널로 향하는 링크를 첨부한다. 상품을 제공하는 은행들은 정해져 있기 때문에, 각 상품의 은행으로 보내준다. (상품별로 보내주는 것은 어렵다. 실제 앱과 콜라보를 하지 않는 이상은)

           

  - 금융 상품 추천 데이터 흐름에서 발생할 수 있는 예외사항에 대해 알아보자

    1. 고객의 요청이 해석하기 애매한 경우
       - 사용자가 설정한 조건 중에서 "A 은행을 다시 추가해줘" 라고 했다고 한다면, 이 A 은행을 제외하는 은행 목록에 추가 해달라고 하는걸까? 아니면 제외 목록에서 검색 가능한 은행으로 다시 추가해달라는 걸까? AI가 해석하는데 어려움이 있을 수 있다. 이런 부분은 어떻게 해결할 것인지 기준을 정해야한다.
    2. 필터링 결과 상품이 0개 존재하는 경우
       - 사용자에게 현재 설정한 조건으로 해당하는 제품은 존재하지 않는다고 안내하고, 검색 조건을 변경해볼 것을 제안한다.
    3. 사용자가 받은 결과에서 다른 조건으로 검색해달라고 요청하는 경우 조건을 어떻게 할 것인지?
       - 사용자가 설정한 조건으로 결과를 받아봤는데 AI에게 "납입 기간을 24개월 까지 늘려줄래?" 라고 추가 요청을 했다면, AI는 나머지 조건을 유지하고 납입 기간만 변경할 것인지? 아니면 전부 초기화 후, 납입 기간만 24개월로 설정하여 검색할 것인지? 에 대한 기준이 필요하다.



## 2) 서비스 흐름 시나리오의 개수

> 서비스 흐름의 시나리오를 정말 다양하게 이용하는 사용자들의 관점에서 판단하면 정말 좋겠지만, 이를 감히 상상하는 것도 어렵고 너무 많이 채우려고 하면 설계에 시간이 너무 많이 소모될 것이다. 그렇기 때문에 MVP 기능의 큰 흐름을 하나 잡고 이 시나리오를 진행할 때 필요한 기능들을 생각해보자.
>
> 그리고 발생할 수 있는 예외를 많이 생각해서 이를 보완하자!



# 2. 논리 아키텍쳐 초안 작성

> 서비스 흐름에서 “사용자가 무엇을 한다”까지 정했다면, **논리 아키텍쳐 초안**은 **그 행동을 처리하기 위해 어느 부분이 무슨 일을 하고, 서로 어떤 정보를 주고받는지** 정한다.



## 1) 시스템 내부와 외부에 요소를 찾기

> 먼저 시스템 내부와 외부의 요소들을 찾아야한다.
>
> 시스템 내부의 요소는 `상담 화면`, `추천 서버`, `저장소` 등이 있다.
>
> 시스템 외부의 요소는 `사용자`, `금융 상품 추천 API`, `금융회사 상품 가입 채널`, `외부 AI API` 등이 있다.
>
> C4 모델의 **시스템 컨텍스트 다이어그램**에서는 우리 서비스를 하나의 박스로 묶고 사용자·외부 시스템과 연결되는 목적을 표시한다. 내부의 상담 화면·추천 서버·저장소까지 펼친 그림은 별도의 내부 논리 구조로 구분한다. 이후 애플리케이션·저장소 단위를 정하면 컨테이너 다이어그램으로 구체화할 수 있다.
>
> ![시스템 컨텍스트 다이어그램](https://c4model.com/images/examples/SystemContext.png)

- 컨텍스트 수준에서는 우리 서비스와 사람·외부 시스템을 박스로 두고 관계를 표시한다. 내부 구조 수준에서는 화면·서버·저장소의 연결 목적을 표시한다. 공시 수집·갱신 기능도 내부 책임으로 식별하되 별도 서버가 반드시 필요한 것은 아니다.

- 이 프로젝트의 [시스템 컨텍스트 및 내부 논리 구조 초안](./시스템_컨텍스트_및_논리_아키텍처_초안.md)에 두 수준의 이미지와 책임 분담, 시나리오 보완 제안을 정리했다. [C4 공식 컨텍스트 설명](https://c4model.com/diagrams/system-context)과 [컨테이너 설명](https://c4model.com/diagrams/container)을 2026-11-24 확인했다.



## 2) 서비스 흐름에서의 행동을 시스템의 행동으로 변경

> 이제 `서비스 흐름` 단계에서 생각했던 `행동`을 `시스템의 행동`으로 변경해보자.
>
> - "A은행은 다시 포함해줘" 라는 서비스 흐름의 행동
>   1. `화면` -> `서버`로 사용자 문장과 어느 상담인지 식별할 정보를 보낸다.
>   2. `서버`는 이전에 설정한 조건들을 보고, `AI`에 문장을 해석하는 데 필요한 대화 맥락을 전달한다.
>   3. `AI` -> `서버`로 `A은행을 검색 대상에 다시 포함` 이라는 변경 의도를 돌려준다. 어느 목록에 포함할지 모호하면 화면에 확인 질문을 보여준다.
>   4. `서버`는 확인된 요청에 따라 제외 목록에서 `A 은행`을 빼고, 월 납입액과 기간을 유지해서 상품 데이터를 다시 조회한다.
>   5. `서버` -> `화면`으로 실제 적용한 조건과 후보 목록을 보낸다. 0건이면 화면에 그 상태를 보여주고, 사용자가 어떤 조건을 바꿀지 선택할 수 있게 한다. 
>
> 위와 같이 하나의 요청에서 각 부분이 어떤 순서로 협력하며 진행되는지를 보여주는 그림을 `시퀀스 다이어그램`이라고 한다. 하지만 시퀀스 다이어그램은 복잡한 상호 작용이 필요한 흥미롭거나 반복되는 패턴 또는 특징을 보여줄 때만 드물게 사용해야 한다. (매번 작성하는 것이 어렵기 때문)
>
> ![동적 다이어그램](https://c4model.com/images/examples/Dynamic-Sequence.png)
>
> - 시퀀스 다이어그램의 예시 사진



# 3. 데이터 설계

> 이제 `시스템의 행동`을 보면서 **그 행동에 필요한 데이터가 무엇이고, 어디서 얻을 수 있는지 확인해야 한다.**
>
> 여기에 더해서 **처리한 뒤 무엇을 저장하거나 화면에 돌려줄지**까지 판단하면 `API`와 `ERD 설계`로 이어진다!

## 1) 시스템 행동에서 필요한 데이터를 찾기

> 예시로 `"A은행은 다시 포함해줘" 라는 상황에서 예시를 들면 아래와 같이 볼 수 있다.
>
> | 시스템의 행동                | 필요한 데이터와 출처                                         | 처리 결과                                                    |
> | ---------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
> | 요청을 해석한다.             | 1. 화면에서 받은 메시지 (출처 : 화면)<br />2. 직전 대화 맥락 (출처: 이전 대화 기록(서버?)) | "A은행을 검색 대상에 다시 포함" 이라는 변경 의도             |
> | 검색 조건을 바꾼다.          | 1. 해당 상담의 직전 확정 조건 (출처 : 이전 대화 기록)<br />2. AI가 처리한 변경 의도(출처: AI 결과) | 직전의 확정 조건에서 `A은행`을 제외 대상에서 제거            |
> | 새 조건으로 후보를 조회한다. | 1. 변경된 조건 (출처: 서버가 검증하고 사용자가 확인한 조건)<br />2. 금융 상품 데이터 (출처: DB에 저장된 값) | 1. 이번 조건에 따른 후보 목록 결과<br />2. 이번에 적용한 조건들 |

- 위와 같이 행동에 따라서 필요한 데이터, 그리고 해당 데이터의 출처를 생각하고, 반환하는 값은 어떤 값인지를 생각하면, DB에 저장해둬야하는 값과 API가 반환해야하는 값을 알 수 있다. 이를 기반으로 API와 ERD를 작성한다.


# 4. 데이터 검증

> 필요한 데이터 중 외부에서 가져오는 데이터들은 기능에 필요한 데이터들을 가지고 있는지 확인이 반드시 필요하다. 그리고 해당 정보들을 DB에 저장하여 어떻게 사용하여 기능을 돌릴 것인지 설계해야한다.

# 5. ERD 및 API 설계

> 이제 필요한 데이터를 검증까지 완료했다면 이를 기반으로 ERD와 API를 설계한다.
>
> API는 서로 주고받는 데이터의 흐름을 보고 작성하면 된다.
>
> ERD는 데이터 끼리의 관계를 보고 작성하면 된다.

# 6. 실제로 프로젝트에 접목시켜보기
