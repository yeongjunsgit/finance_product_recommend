# AI 기반 금융 서비스 기획 문서



## 1. 서비스 제공 이유 (페르소나)

- 보통 사람들은 금융 상품에 가입하려고 하면 자신의 상황은 생각해둔다.
  - 예, 적금 상품의 경우
    - 매달 얼마를 넣을지
    - 기간은 어느정도로 할지
    - 금리는 어느 정도 이상 바라는지
  - 대출 상품의 경우
    - 얼마를 대출할지
    - 대출 기간 및 이자는 얼마정도로 할지

- 그러나, 내 상황과 계획에 맞는 상품을 찾기가 어렵고, 주 거래 은행이 아닌 곳에서도 거래를 하려고 한다면 귀찮게 각각의 은행을 전부 방문해서 찾아야 하며 비교 분석하는게 까다롭다.
- 이 서비스는 다양한 은행의 금융 상품 중에서 내 상황에 맞는 상품을 추천받고, AI와 함께 추천 범위를 줄여가며 나에게 맞는 상품을 찾는 서비스이다.



### 문제 1) 근데 이걸 굳이 AI로 할 필요가 있나?

- 그런데 단순히 필터링만 거쳐가는 서비스라면 AI를 사용할 필요가 있을지 의문이다. 어떻게 경쟁력을 강화할 수 있을까?



## 2. 새로운 서비스 흐름

```
사용자 상황과 목표
- 나는 이사 비용 마련을 위해서 1년 정도 기간으로 매달 50만원 가량 넣을 수 있는 적금을 찾고 싶다.
- 이율이 좀 좋은 상품으로 찾고싶다!

정상 흐름
0. 서비스가 금융상품통합비교공시 API를 이용해 DB에 상품들을 저장 및 갱신한다.
1. 사용자가 사이트에 접속하여 AI에게 1년 정도 기간으로 매달 50만원을 넣을 수 있는 이율이 좋은 적금을 찾아달라고 한다.
2. 서비스가 사용자의 요청을 분석하고 요청에 맞는 결과를 제공한다. 이때, 사용자의 요청이 해석이 어렵거나 모호한 경우에는 질문하여 확답을 얻는다.
3. 사용자가 주어진 상품들을 보고 추가로 조건을 제시해서 다시 필터링을 한다.
4. 서비스가 사용자의 추가 요청을 기존 요청에 더해서 다시 결과를 제공한다.
5. 3~4를 반복하고 서비스가 최종적으로 사용자가 원하는 금융상품의 가입 채널로 이동할 수 있도록 해당 상품을 판매하는 은행의 링크를 제공한다.

비교가 끝났다고 볼 수 있는 순간
- 사용자가 할 수 있다.

예외 한 가지
- 확인한 조건에 맞는 상품이 0개라면 서비스는 현재 조건에 만족하는 상품이 없다고 안내하고,
  사용자는 다음으로 현재 조건을 AI와 대화하며 변경하여 다른 상품을 찾아볼 수 있다.
```

### 0) 서비스가 금융상품통합비교공시 API를 이용해 DB에 상품들을 저장 및 갱신한다.

1. `수집 기능`이 오전 9시(임시, 한국 시간)에 API를 호출한다.

2. `서버`가 응답 오류와 수집 대상 권역·페이지의 누락을 확인한다.

3. 수신한 원문과 수집 시각·공시 기준일을 저장한다.

4. 상품 식별 기준으로 기존 데이터와 비교해 **신규·변경·미등재**를 구분한다.

   - 상품 갱신을 할때 기준이 필요하다.

     - **상품코드 단독 비교보다 금융회사·상품군·상품코드의 조합**을 식별 기준으로 검토한다. 실제 유일성은 실응답으로 확인해야 한다.

     - 정상적으로 전체 수집을 완료했는데 상품이 빠졌다면 **미등재 처리하고 신규 추천에서 제외**한다. 과거 기록은 보존한다.

     - 상품 전체와 기간별 옵션을 구분한다. **24개월 옵션만 없어졌다고 상품 전체를 제외하지 않는다.**

5. 숫자·날짜·코드처럼 규칙으로 처리할 데이터는 `서버`가 변환한다.

6. 문장과 해석에 필요한 맥락이 달라진 항목만 `AI`에 정제를 요청한다.

7. `서버`가 정제 결과를 검증하고 해당 원문 버전과 연결해 저장한다.

8. 검증된 데이터를 추천에 사용한다.

- 추가적인 조사가 필요하다. 매번 정제를 하면 토큰 소모가 너무 커지기 때문에 어떤 기준으로 정제하고 갱신할지 확인한다.

  - 갱신이 필요한 컬럼을 추려내고 해당 컬럼만 정제한다.

  - 매번 모든 값들을 정제하지 않고, 변경점이 있는 컬럼만 정제한다.

  - 추가되는 상품과 사라지는 상품들의 확인을 위해 DB에 저장된 상품들과 새롭게 받은 상품들의 상품코드를 비교한다. DB에 있는 상품이 새로운 데이터에 없다면 제거, 새로운 데이터에 있는 상품이 DB에 없다면 DB에 추가한다.



### 1) 사용자가 사이트에 접속하여 AI에게 1년 정도 기간으로 매달 50만원을 넣을 수 있는 이율이 좋은 적금을 찾아달라고 한다.

1. `화면`이 사용자 메시지와 상담 식별 정보를 `서버`에 전달한다.
2. `서버`가 **현재 적용 조건, 필요한 최근 대화, 답변 대기 중인 질문, 직전 추천 정보**를 조회한다.
3. `서버`가 필요한 맥락과 사용자 메시지를 `AI`에 전달한다.
4. `AI`가 요청을 해석해 조건 변경 내용 또는 확인 질문을 제안한다.
5. `서버`가 해석 결과를 검증하고 분기한다.
   - **확인 필요:** 질문과 선택지를 `화면`에 전달하고 답변을 기다린다. 확인되지 않은 조건으로 기존 확정 조건을 덮어쓰지 않는다.
   - **처리 가능:** 명확한 요청을 현재 조건에 반영하고, 변경하지 않은 조건은 유지한다.
6. `서버`가 적용 조건으로 `DB`에서 후보를 조회하고 필터링·계산·정렬한다.
7. 조회 결과에 따라 분기한다.
   - **0건:** 결과 없음과 적용 조건을 전달하고, 완화 가능한 조건을 제안한다. 사용자 요청·확인 없이 조건을 바꾸지 않는다.
   - **후보 있음:** 추린 후보·계산 결과·비교 근거·미확인 사항을 `AI`에 전달해 추천 설명을 받는다.
8. `서버`가 설명을 검증하고 **이번 추천 조건과 결과를 저장**한다.
9. `서버`가 적용 조건·상품 카드 데이터·설명을 `화면`에 전달한다.
10. `화면`이 이를 표시하고, 사용자의 추가 요청이 오면 같은 상담에서 반복한다.



### 2) 회원 기능을 통해 이전 추천 기록을 확인한다.

1. 로그인한 `사용자`가 이전 추천 기록을 요청한다.
2. `서버`가 로그인 인증 정보로 사용자를 식별한다.
3. `서버`가 **해당 사용자 소유의 기록만** `DB`에서 조회한다.
4. `서버`가 추천 당시 조건·결과·기준 시점을 `화면`에 전달한다.
5. `화면`이 과거 기록임을 표시하고 사용자에게 보여준다.
6. 사용자가 “현재 조건으로 다시 추천”을 요청하면 최신 데이터로 새 추천을 실행한다.

추가 확인 사항: 전체 JSON 변경 여부와 AI 재정제 필요 여부는 다르다. 금리만 변경되고 정제 문장·참조 맥락·정제 기준이 동일하다면 문장 정제는 재사용할 수 있지만, 이자 계산과 적합성 검증은 새 값으로 갱신한다. 상품의 특정 기간 옵션만 미등재라면 해당 옵션만 추천에서 제외한다. 연금저축은 기존 검토 문서의 이관된 출처·조회 기간을 적용하며 동일한 Finlife 응답 형식을 가정하지 않는다.
