## 1. 개요

### 1.1 서비스 목적과 범위

금융감독원 금융상품통합비교공시 API로 상품 정보를 수집하고, 사용자의 목적·금액·기간·이용 은행·선호·상환 계획 등을 확인하여 금융상품을 추천한다. 사용자는 AI 상담 또는 일반 상품 탐색으로 후보를 찾고, 조건을 비교한 뒤 금융회사의 공식 가입·상담 경로로 이동한다.

핵심 가치는 **추천을 받아보며 자신에게 중요한 조건을 발견하고, 누적된 조건을 확인·수정하면서 선택을 구체화하는 것**이다. 사용자가 처음부터 모든 제약사항을 알고 설명한다고 전제하지 않는다. 예·적금은 목표 시점과 우대조건, 대출은 자금 목적과 상환 부담·비용·금리 변동 위험을 고려한다. 서로 목적이 다른 상품을 하나의 금리 순위로 섞지 않는다.

| 구분 | MVP 범위 |
|---|---|
| 핵심 기능 | AI 상황별 금융상품 추천 |
| 지원 기능 | 회원, 개인화 설정, 일반 조회·비교, 공식 가입·상담 채널 연결 |
| 상품 | 예금·적금, 주택담보·전세자금·개인신용·개인사업자대출 |
| 개인 정보 확보 | 사용자가 직접 입력하거나 대화에서 확인한 정보 |
| 미포함 | 직접 계약·이체·대출 실행, 실제 승인금리·한도 조회 연동, 계좌 자동 연동, 보유 계약 자동 진단 |
| 후속 검토 | 알림, 목표 설계 고도화, 상담 간 자동 장기 기억, 주변 지점 지도 |

대출은 MVP에 포함한다. 공시 기반 후보 추천과 금융회사의 개인 심사·승인은 별개의 기능이다. 연금·보험 등은 이번 확정 범위에 포함하지 않는다.

### 1.2 해결하려는 문제와 차별화

최고 예금금리나 최저 대출금리만으로는 적합성을 판단하기 어렵다. 실제 충족 가능한 조건, 돈이 필요한 날짜, 월 저축·상환 여력, 조기상환 계획 등이 결과에 영향을 준다.

사용자는 자신의 목적과 예산을 이야기할 수 있어도, 어떤 상품 조건을 살펴봐야 하는지 처음부터 알기는 어렵다는 문제 가설을 둔다. 핵심 사용자는 추천 상품의 조건을 접한 뒤 자신에게 부담스러운 조건이나 수용 가능한 조건을 발견하며 선택 기준을 구체화하는 사람이다. 이 가설과 사용자 유형은 실제 사용자 인터뷰로 검증해야 한다.

기존 금융 플랫폼도 비교·개인화를 제공한다. 본 프로젝트는 AI 사용 자체를 독창성으로 주장하지 않고, **상황 입력 → 1차 추천과 상품 조건 이해 → 사용자 반응 → 누적 조건 확인·수정 → 재추천과 차이 설명**을 반복하는 경험에 집중한다. 사용자는 조건을 추가하는 것뿐 아니라 기존 조건을 바꾸거나 해제할 수 있다.

예를 들어 “6개월 후 대출을 갚을 예정”이라는 답변이 추가되면, 최저금리뿐 아니라 그 시점까지의 이자와 확인된 중도상환수수료를 비교한다. “매달 일정한 금액으로 상환하고 싶다”면 해당 상환 구조를 설명하고 공시에서 확인되는 옵션을 우선 검토한다.

### 1.3 공식 API 확인 범위와 출처

아래 공식 페이지의 결과변수 표를 브라우저에서 직접 확인했다. 주택담보·사업자 요청변수와 개인신용대출의 JSON 예제도 확인했다. **인증키로 최신 상품 전체를 호출한 검증은 하지 않았다.** 예제의 오래된 금리·공시월은 현재 조건으로 사용하지 않는다.

### 1.5 데이터의 한계

공시 최저금리·한도는 개인의 승인금리·승인한도가 아니다. 구간별 신용금리도 개인 확정 견적이 아니다. 공시 날짜는 개인 가입일·만기일이 아니며 등재 여부도 실시간 판매 여부와 다르다. 과거 상품이나 개인 계약을 자동 복원할 수 있다고 전제하지 않는다.

API에 없는 정보, 사용자에게 받는 정보, 금융회사에 추가 확인할 정보를 분리한다. 가입 방법 문구만으로 상품별 연결 URL을 확보할 수 없으므로 공식 링크는 별도로 검증한다.

## 2. 기능 설명

### 2.1 AI 추천의 공통 흐름

1. 사용자가 자신의 상황과 저축·대출 목적을 자연어로 설명한다.
2. 상품군·금액·기간 등 해당 비교에 꼭 필요한 정보가 부족할 때 추가 질문한다. 모든 선호와 제약사항을 첫 추천 전에 입력하도록 요구하지 않는다.
3. 사용자가 파악된 조건을 확인·수정하면 서버가 후보를 필터링·계산·정렬해 1차 추천을 제공한다. 미응답 선호는 동의나 거부로 간주하지 않는다.
4. 추천 이유와 함께 가입·우대조건, 필요한 행동, 미확인 사항을 보여준다. 우대 충족이 확인되지 않은 최고금리를 사용자가 받을 금리로 단정하지 않는다.
5. 사용자가 추천을 보고 부담스러운 조건이나 새 선호를 이야기하면, 직전 확정 조건에 대한 추가·변경·해제 내용을 정리한다. 모호한 요청은 확인한다.
6. 변경하려는 내용과 누적된 전체 조건을 함께 보여주고 사용자가 확인·수정할 수 있게 한다. 변경하지 않은 기존 조건은 유지한다.
7. 재추천 결과와 직전 결과의 차이·이유를 설명하고 4~6단계를 반복한다. 후보가 없으면 충돌하거나 완화할 수 있는 조건을 설명하고 사용자 확인 없이 조건을 해제하지 않는다.
8. 사용자가 선택한 상품의 검증된 공식 가입·상담 경로로 연결한다.

예를 들어 사용자가 월 50만 원·12개월 적금을 추천받은 뒤 “급여이체 조건은 빼줘”라고 하면, 상품의 조건 자체를 삭제하는 것이 아니라 급여이체를 하지 않는 기준으로 비교한다. 급여이체 없이 가입 가능한 상품은 해당 우대를 제외한 조건으로 비교할 수 있다. 요청이 급여이체 조건이 있는 상품 전체의 제외를 뜻하는지 모호하면 확인한다. 이후 “새 은행 계좌 개설은 괜찮아”라고 하면 기존 금액·기간과 급여이체 선호를 유지하면서 해당 선호를 반영한다. 현재 적용 조건은 추천과 함께 반복해 보여주며 수정·해제를 지원한다. 구체적인 화면 표현은 후속 설계에서 정한다.

AI는 자연어 이해·추가 질문·조건 추출 제안·설명을 담당한다. 금리 처리와 계산·규칙 적용은 서버 로직에서 수행한다. 기본 알고리즘은 AI 추천의 계산 기반이며, 별도 기본 추천 화면 제공 여부는 추후 결정한다. 정보가 부족하면 조건을 확인하고 순위를 보류하거나 비교 제한을 표시한다.

### 2.2 상품군별 질문과 추천 기준

| 상품군 | 사용자에게 확인할 상황 | 추천 기준 | 확인되지 않는 사항 |
|---|---|---|---|
| 예금·적금 | 목돈·월 저축액, 목표일, 우대조건 수행 의향 | 기간·한도 적합성, 예상 이자, 조건 부담 | 실제 우대 충족·중도해지 조건 |
| 주택담보 | 목적, 담보유형·가액, 금액·기간, 상환·금리 선호, 조기상환 계획 | 담보·상환·금리 유형 일치, 금리 범위, 부대·중도상환 비용 | 개인 한도·담보평가·실제 제공 기간 |
| 전세자금 | 보증금·자기자금, 금액·필요일, 계약기간·상환 선호 | 공시 한도 설명과 수요, 상환방식, 금리·비용 | 보증기관·주택·계약 적격성, 보증료·실행 일정 |
| 개인신용 | 목적·금액·기간, 점수·평가사, 월 상환 여력 | 같은 대출종류·평가사·점수 구간의 대출금리 | 개인 한도·가입자격·기간·상환방식·수수료 |
| 개인사업자 | 용도·금액·기간, 필요한 업력·업종·매출, 상환 계획 | 용도·가입조건·기간·한도, 우대·상환·금리 방식·총비용 | 실제 사업자 자격·심사 소득·담보·보증·승인 |

위 기준은 공식 제공 데이터를 바탕으로 한 설계 제안이다. 소득·부채·사업 정보는 API가 제공하는 고객 정보가 아니라 필요할 때 사용자가 입력하는 정보다. 이를 모든 회원의 가입 필수항목으로 요구하지 않는다.

### 2.3 대출 추천에서 지켜야 할 비교 원칙

**목적을 먼저 맞춘다.** 주택담보·전세·신용·사업자를 최저금리만으로 섞지 않는다. 확인 가능한 용도와 조건에 맞는 후보 안에서 비교한다.

**같은 금리 지표를 비교한다.** 대출금리와 기준·가산·가감조정금리를 구분한다. 이미 대출금리가 있는데 구성요소를 다시 더하지 않는다. 같은 CB와 점수 구간을 우선 비교하고 KCB·NICE 점수를 임의 환산하지 않는다. 구간값이 없으면 평균으로 대체했음을 표시하거나 비교에서 분리한다.

**월 상환액과 총비용을 함께 본다.** 원금·기간·금리·상환방식이 확보된 경우에만 시나리오를 계산한다. 공시 범위로 계산한 값은 개인 견적이 아니다. 비용이 일부 미확인되면 누락 항목을 표시한다. 변동금리는 현재 가정과 금리 상승 시나리오를 구분하고 미래금리를 예측했다고 표현하지 않는다.

**조기상환 계획을 반영한다.** 단기간 내 상환할 계획이면 해당 기간의 이자와 중도상환수수료·초기 비용을 함께 본다. 수수료 적용 기간·면제 요건이 불명확하면 확정 계산을 하지 않는다.

**상환 부담과 승인 판단을 구분한다.** 입력한 월 상환예산을 넘는지 보여줄 수 있지만 금융회사의 승인·거절을 결정하지 않는다. DSR·LTV 충족을 공시만으로 확정하지 않는다. 규제 계산을 도입하려면 최신 규칙·적용 대상·소득과 부채 산정 기준을 별도 검증한다.

**기준일과 확인 필요 사항을 표시한다.** 낮은 공시금리 때문에 반드시 대출받을 수 있다고 안내하지 않는다. 실제 금리·한도·실행 가능 여부는 금융회사 확인 항목으로 남긴다.

### 2.4 회원과 개인화 설정

이메일 기반 가입·로그인·로그아웃·탈퇴를 초안으로 한다. 비밀번호는 해시만 저장한다. 이용 금융회사, 주거래·급여은행, 채널 선호, 추가 거래 조건에 대한 의향을 공통 설정으로 관리한다. 미응답은 거부와 구분한다.

공통 선호와 이번 상담의 조건을 분리하고, 확인된 상담 조건을 우선한다. 저축 여력과 대출 상환 여력은 다른 값이다. 신용점수는 평가사·기준일과 함께 대출 상담에 기록한다. 소득·부채·담보·사업 정보는 해당 상담에 필요한 경우에만 받는다. 가정 질문을 실제 프로필로 자동 저장하지 않는다.

회원은 본인 데이터만 조회·수정할 수 있다. 탈퇴 시 개인 정보가 포함된 메시지와 추천 스냅샷도 삭제 정책에 포함한다.

### 2.5 일반 상품 조회·비교

상품군별 목록·상세·필터를 제공한다. 저축은 기간·적립방식·우대조건, 주담대·전세는 상환·금리유형, 신용·사업자는 상품종류·점수 구간 등 실제 제공 항목으로 탐색한다. 사용자가 직접 고른 후보도 AI 상담에서 비교할 수 있다.

기본·최고 우대금리와 대출의 최저·최고·구간별 금리를 각각 맞는 의미로 표시한다. 비교 금액·기간 등 가정을 맞추고 정보 기준일과 미확인 조건을 함께 제공한다. 상품 조회와 추천은 같은 데이터 원천을 사용한다.

### 2.6 가입·상담 채널 연결

공식 웹·앱·영업점 안내를 제공한다. `join_way`와 실제 연결 URL은 별도로 관리하고 출처·확인일을 기록한다. 검증되지 않은 경로는 신청 버튼으로 노출하지 않는다. 대출은 공식 조건 확인·상담·신청 경로로 연결하며, 이동 자체를 신청·승인·실행 완료로 기록하지 않는다. 지도나 상품별 앱 딥링크는 후속 검토 범위다.

## 3. ERD 및 데이터 설계

### 3.1 전체 구조

공통 11개와 유형별 상세 6개, 총 **17개 테이블**이다. 첫 그림은 공통 구조, 두 번째는 상세 구조다. 두 번째 그림의 회색 상자는 첫 그림의 테이블을 다시 표시한 참조이며 새 테이블이 아니다.

![공통 ERD](./finance-mvp-erd.png)

![상품 유형별 상세 및 대출 상담 ERD](./finance-mvp-erd-details.png)

PK는 기본키, FK는 다른 테이블을 참조하는 외래키, UQ는 중복 방지 제약이다. 1:N의 자식 행은 0개일 수도 있다. 1:0..1은 없거나 한 개라는 뜻이며, 상품 유형에 따라 필요한 상세행은 저장 트랜잭션과 유형 검사로 반드시 생성하도록 보장한다.

상품·상담·추천의 공통 구조는 유지하고 저축과 대출의 다른 속성은 별도 상세 테이블로 분리한다. 예금의 최고 우대금리와 대출의 최고금리를 같은 필드로 합치지 않는다.

### 3.2 회원·개인화 테이블

#### users — 회원 식별과 로그인

**역할:** ID, 유일한 이메일, 비밀번호 해시, 표시 이름, 생성·수정 시점을 저장한다. **이유:** 설정과 상담 소유자의 기준점이다. 인증 정보와 금융 입력을 분리해 가입 부담을 줄인다. 회원은 프로필 하나와 여러 이용은행·상담을 가질 수 있다.

#### user_profiles — 공통 선호

**역할:** `user_id`를 PK/FK로 사용하고 선택적 연령대·저축 여력, 채널 선호, 새 은행·급여이체 변경·카드 사용·자동이체 의향을 저장한다. **이유:** 반복 질문을 줄이고 여러 상담에서 확인된 선호를 재사용한다. 미응답은 NULL이다. 정확한 나이 제한을 연령대만으로 판정하지 않는다. 대출 상세 정보는 여기에 일괄 수집하지 않는다.

#### user_banks — 이용 금융회사 연결

**역할:** `(user_id, institution_id)` 복합 PK와 주거래·급여은행 여부를 저장한다. **이유:** 여러 회원과 여러 은행의 다대다 관계를 중복 문자열 없이 표현한다. 주거래 은행은 회원당 최대 하나로 제한한다. 이용은행 등록은 실제 거래실적 검증을 의미하지 않는다.

### 3.3 상품 공통 테이블

#### institutions — 금융회사 기준 정보

**역할:** 내부 ID, 외부 코드 `fin_co_no`, 이름·권역·확인된 홈페이지·수집일을 저장한다. **이유:** 저축·대출과 회원 설정이 동일 금융회사를 일관되게 참조한다. 회사 하나에 여러 상품이 연결된다. 상품군별 지원 권역은 수집 설정에서 구분한다.

#### products — 공통 상품 식별·공시

**역할:** 회사 FK, `product_type`, `fin_prdt_cd`, 이름, 가입방법, 원천 API, 공시·수집일, 등재 상태, 원문 `raw_payload`를 저장한다. **이유:** 모든 조회·채널·추천의 공통 기준점이다. 유일키는 `(institution_id, product_type, fin_prdt_cd)`다. 유형은 DEPOSIT, SAVING, MORTGAGE, JEONSE, CREDIT, BUSINESS_LOAN으로 구분한다. 저축 우대조건과 대출 비용은 유형별 상세로 이동한다.

#### product_options — 공통 추천 대상

**역할:** 상품 FK, `option_key`, `option_family`, 등재·수집 정보를 저장한다. **이유:** 추천 결과가 모든 상품군을 하나의 실제 FK로 참조할 수 있게 한다. 유일키는 `(product_id, option_key)`이며 금리나 수집일을 옵션 식별키에 넣지 않는다.

저축은 기간·이자·적립유형, 주담대는 담보·상환·금리유형, 전세는 상환·금리유형을 키로 사용한다. 개인신용은 상품 내 대출종류·CB 기준으로 옵션을 만들고 금리구분별 행은 `credit_rate_points`로 모은다. 사업자 옵션의 실제 구분 차원은 실응답 검증 후 확정한다. 단일 옵션이면 명시적 기본 키를 사용하고 복수 행을 임의 덮어쓰지 않는다.

#### product_channels — 공식 가입·상담 경로

**역할:** 상품 FK, 채널 종류, 표시 이름, 공식 URL·안내, 근거 URL, 검증 상태·일자를 저장한다. **이유:** 상품 하나에 여러 경로가 있고 공시와 링크의 변경 주기도 다르기 때문이다. URL 없는 영업점 안내도 허용한다. 계약이나 대출 실행 내역을 저장하는 테이블이 아니다.

### 3.4 상품 유형별 상세 테이블

#### savings_product_terms — 저축 기본 조건

**역할:** 상품 ID를 PK/FK로 사용하고 `join_deny`, `join_member`, `spcl_cnd`, `etc_note`, `mtrt_int`, `max_limit`를 저장한다. **이유:** 저축의 가입·우대·만기 후 조건을 대출과 구분한다. 저축 상품에 상세행 하나를 둔다.

#### loan_product_terms — 대출 기본 조건

**역할:** 상품 ID를 PK/FK로 사용하고 비용·중도상환·연체 정보, 한도 설명, 대출종류·CB, 사업자 용도·기간·가입조건·우대금리를 저장한다. **이유:** 대출 고유 정보를 보존하면서 API가 제공하지 않는 속성은 비워둘 수 있게 한다.

`loan_lmt`와 사업자 `loan_limit`는 `loan_limit_text`, `loan_limit_detl`은 `loan_limit_detail`로 매핑한다. 사업자 `join_deny`와 `join_deny_detl`은 `join_condition_text`·`join_condition_detail`로 변환한다. 신용 대출종류는 `credit_product_type`, 사업자 상품구분은 `business_product_type`으로 구분한다. `loan_term_text`, `repayment_type_text`, `rate_type_text` 등은 원문을 보존하고 원천 필드를 기록한다. 신용대출에 없는 비용·한도는 NULL이다.

#### savings_option_terms — 저축 옵션 금리

**역할:** 옵션 ID를 PK/FK로 사용하고 저축기간, 이자·적립유형, 기본·최고 우대금리를 저장한다. **이유:** 같은 상품의 기간별 수익을 구분한다. 예금의 적립유형은 N/A로 정규화한다. 금리는 DECIMAL이며 결측을 0으로 채우지 않는다.

#### loan_option_terms — 대출 방식과 금리 범위

**역할:** 옵션 ID를 PK/FK로 사용하고 담보·상환·금리유형, 최저·최고·전월 평균금리, 코드명·원천 필드를 저장한다. **이유:** 주담대·전세·사업자의 같은 방식끼리 범위금리를 비교한다. 담보유형이 없는 유형은 NULL이다. 사업자의 방식은 기본정보에서, 금리 범위는 옵션에서 매핑한다. 개인신용에는 없는 범위금리를 만들어 넣지 않는다.

#### credit_rate_points — 점수 구간별 금리

**역할:** 옵션 FK, 금리 지표 `rate_kind`, 구간키 `band_key`, 점수 하한·상한, 금리값, 원천 필드를 저장한다. 유일키는 `(option_id, rate_kind, band_key)`다. **이유:** 신용·사업자의 다른 가로형 필드를 행으로 정규화하고 대출금리와 구성요소를 구분한다.

평균은 `band_key=AVG`, 점수 경계는 NULL이다. 900점 초과는 901 이상으로 변환한다. CB는 상품 상세를 참조한다. 사업자 옵션은 이 테이블과 `loan_option_terms`를 함께 가질 수 있다. 0은 실제 0인지 미공시 표현인지 확인한 뒤 해석하며 원문을 보존한다.

### 3.5 상담·추천 테이블

#### consultations — 상담별 목적과 상태

**역할:** 회원 FK, 상품군, 제목·상태, 목표 종류·날짜·금액, 저축 목돈·월 납입액, 제약조건, 확인시점을 저장한다. **이유:** 한 회원의 저축·이사·사업자금 상담을 분리한다. 대출 상담에서는 저축용 필드를 비워두고 대출 상세 입력을 사용한다.

#### consultation_loan_context — 대출 상담 입력

**역할:** 상담 ID를 PK/FK로 사용하고 목적, 요청금액, 희망기간, 필요일, 상환·금리 선호, 조기상환 계획, 월 상환예산을 저장한다. 필요시 점수·평가사·점수 기준일, 연소득, 기존 연간 원리금 부담, 담보유형·가액, 보증금, 사업 정보도 저장한다. **이유:** 저축과 대출의 입력 의미를 구분하고 상담에 필요한 항목만 수집한다.

사용자가 확인한 입력이며 API로 검증된 값은 아니다. `business_context`는 필요한 업종·업력·매출 등을 스키마를 정의해 저장한다. 원문 서류·계좌번호·주민등록번호를 기본 입력으로 요구하지 않는다. 미응답은 NULL이며 `confirmed_at`과 스키마 버전을 둔다.

#### consultation_messages — 질문·응답 원문

**역할:** 상담 FK, 순번, 발화자, 내용, 작성일을 저장한다. **이유:** 현재 상담에서 질문과 답변을 연결하고 조건 추출 근거를 확인한다. `(consultation_id, sequence_no)`는 유일하다. 여러 상담에 걸친 자동 장기 기억을 구현한다는 뜻은 아니다.

#### recommendations — 추천 실행

**역할:** 상담 FK, 실행 상태·일자, 실제 입력 스냅샷, 모델·프롬프트·알고리즘 버전, 요약·오류를 저장한다. **이유:** 조건 변경마다 새 실행을 남겨 결과가 달라진 이유를 설명한다. 스냅샷에는 실제 사용한 프로필·이용은행·대출 입력도 포함한다. 이후 설정 변경과 분리하며, 모델 버전만으로 동일 문장 재생성을 보장하지는 않는다.

#### recommendation_items — 후보별 결과와 근거

**역할:** 추천 FK, 공통 옵션 FK, 순위·추천 이유, 조건 판정, 계산 결과·가정, 당시 상품 스냅샷을 저장한다. **이유:** 추천 한 번의 여러 후보와 그 당시 조건을 보존한다. 같은 실행 안에서 순위와 옵션 중복을 막는다.

계산 결과는 `calculation_results` JSON으로 저장한다. 저축의 예상 수령 이자와 대출의 가정별 월 상환액·총이자·수수료·총상환액·누락 비용을 별도 지표로 저장한다. `calculation_assumptions`에는 금액·기간·금리 출처·상환방식·계산일·시나리오를 남긴다. 상품 스냅샷에는 유형별 상세와 구간별 금리도 포함한다. 계산 불가 값을 임의 생성하지 않는다.

### 3.6 관계와 무결성

| 관계 | 의미 |
|---|---|
| users → user_profiles | 공통 설정 0~1개 |
| users → user_banks ← institutions | 이용 금융회사 다대다 |
| institutions → products → product_options | 회사별 상품, 상품별 추천 옵션 |
| products → product_channels | 여러 가입·상담 경로 |
| products → savings_product_terms / loan_product_terms | 유형에 맞는 기본 상세 |
| product_options → savings_option_terms / loan_option_terms | 유형별 옵션 상세 0~1개씩 |
| product_options → credit_rate_points | 구간·지표별 여러 금리 행 |
| users → consultations | 회원별 여러 상담 |
| consultations → consultation_loan_context | 대출 상세 0~1개 |
| consultations → consultation_messages / recommendations | 여러 발화와 추천 실행 |
| recommendations → recommendation_items ← product_options | 후보별 공통 옵션 참조 |

저축은 저축 상세, 주담대·전세는 대출 옵션 상세, 개인신용은 구간별 금리, 사업자는 대출 옵션 상세와 구간별 금리를 연결한다. 유형과 상세의 일치는 저장 트랜잭션과 제약 검사로 보장한다. 추천은 공통 옵션 FK를 유지하며 테이블명과 ID만 저장하는 느슨한 참조는 사용하지 않는다.

### 3.7 구현·운영 원칙

- 공시 원문·기준일·수집일을 보존한다. 전체 수집 성공 후 미등재 상태를 판단하고 수집 실패를 판매 종료로 바꾸지 않는다.
- 과거 추천이 참조하는 상품·옵션은 물리 삭제하지 않고 상태를 변경한다. 회원 탈퇴 시 개인 정보가 있는 대화·스냅샷은 삭제 정책을 적용한다.
- 금리·금액은 DECIMAL로 저장한다. JSON도 필드·타입·버전을 정의하고 중요한 검색·관계는 일반 컬럼으로 관리한다.
- 문장 조건은 원문 근거와 검증 상태를 갖는다. 모든 API가 모든 가입요건·비용·기간을 제공한다고 가정하지 않는다.
- 실응답으로 상품·옵션 식별 조합, 결측, 코드명을 검증한다. 특히 사업자 옵션의 식별 차원은 명세 표만으로 확정하지 않는다.
- 대출 상세 요건을 공식 자료로 보완하면 출처·확인일을 기록하고 공시 값과 구분한다.
- 개인 승인 결과를 조회하지 않은 상태에서 승인 확률이나 확정금리를 생성하지 않는다.

현재 구조는 저축과 대출 4종의 데이터 의미를 유지하면서 상황별 후보 추천·비교·공식 채널 연결을 지원하는 논리 설계다. 실제 DB 타입·인덱스·마이그레이션은 실응답 확인 후 확정한다.
