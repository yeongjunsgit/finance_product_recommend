# AI 금융상품 추천 서비스 인수인계

최종 갱신일 2026-11-16 (한국 시간)

## 필수 학습 원칙

이 프로젝트는 구현과 학습을 함께 진행한다. 다음 원칙은 기술 질문에 답할 때, 기술을 선택할 때, 코드를 작성·수정하고 결과를 설명할 때 모두 적용한다.

- **최신 공식 근거를 확인한다.** 기술을 설명하거나 제안하기 전에 공식 문서, API 명세, 릴리스 노트, 표준 명세 등 1차 출처를 직접 확인한다. 주요 기술 주장이나 선택 근거에는 해당 페이지 링크를 붙이고, 버전에 따라 달라지는 내용에는 적용 버전과 확인일을 적는다. 프로젝트에 이미 사용 중인 버전이 있다면 최신 문서의 내용이 그 버전에도 적용되는지 확인한다.
- **근거와 판단을 구분한다.** 공식 문서가 보장하는 동작, 이 저장소에서 실행해 확인한 결과, 프로젝트에 대한 제안을 각각 알아볼 수 있게 설명한다. 근거를 확인할 수 없으면 어떤 부분이 미확인인지 밝히고, 확인할 문서나 재현 방법을 안내한다.
- **처음 배우는 사람도 따라갈 수 있게 풀어 쓴다.** 전문 용어와 약어는 처음 등장할 때 쉬운 말로 뜻을 설명한다. 기술이 어떤 문제를 해결하는지, 어떤 순서로 작동하는지, 이 프로젝트의 어느 부분에 쓰이는지 연결해 설명한다. 이해에 도움이 되면 실제 프로젝트의 작은 예시를 든다.
- **구현과 검증을 설명한다.** 코드나 명령어를 제시할 때는 주요 단계에서 무엇을 하고 왜 필요한지, 실행 결과에서 무엇을 확인하면 되는지 알려준다. 기술을 선택할 때는 프로젝트 요구사항을 기준으로 선택 이유와 주요 장단점을 설명한다.

## 목표와 범위

금융감독원 금융상품통합비교공시(Finlife) 데이터를 바탕으로 사용자의 목적·금액·기간·선호·상환 계획에 맞는 후보를 비교한다. 사용자가 조건을 추가하거나 바꾸면 후보가 어떻게 달라지는지, 추천 이유와 확인할 사항이 무엇인지 설명하고 금융회사의 검증된 공식 가입·상담 경로로 연결한다.

- MVP 상품은 정기예금, 적금, 주택담보대출, 전세자금대출, 개인신용대출, 개인사업자대출이다.
- 핵심 기능은 AI 상담과 상황별 추천이다. 회원·개인화 설정, 일반 상품 조회·비교, 공식 채널 연결이 이를 지원한다.
- 직접 계약·이체·대출 실행, 개인 승인금리·한도 조회, 계좌 자동 연동, 보유 계약 자동 진단, 연금·보험은 MVP 범위 밖이다.
- 프로젝트에서 검토할 주제는 민감정보 보호, RAG를 통한 추천 설명의 근거 보강, 데이터 조회 성능, 실제 배포다. 기술 스택과 RAG 도입 방식은 결정 전이다.

## 현재 상태

- 추천 설계 초안에 적금 한 건을 따라가는 예제, 20개 테이블의 컬럼·자료형과 관계선, 시스템 연결별 API 입출력·설계 이유를 추가했다. PostgreSQL 자료형은 설계 예시이며 DB 선택과 외부 키 검증은 구현 전에 확정한다.

- [7개 상품군 추천 설계 초안](../docs/적금_추천_설계_초안.md)과 [테이블형 ERD](../docs/savings-recommendation-erd.svg)를 갱신했다. 기존 MVP 배포 범위와 별도로 연금저축 확장 설계를 포함한다. Finlife 6개 결과표 및 연금 이관 안내, 통합연금포털의 현행·과거 상품별 및 보험 명세를 브라우저에서 확인했다. 인증 실응답으로 사업자 옵션 식별, 연금 상품 매핑·분기 경계, 결측과 단위를 검증해야 한다.

- [통합 기획 보고서](../docs/금융상품_추천_서비스_통합_기획_보고서.md)에 기능 범위, 상품군별 API 필드와 한계, 추천 규칙, 17개 테이블의 논리 설계가 있다. 구현 코드와 실행·테스트 환경은 아직 없다.
- 보고서에 따르면 공식 API 명세와 일부 요청·응답 예제를 확인했다. 인증키로 호출한 실응답 검증은 남아 있다. 예제 금리는 현재 상품 조건으로 사용하지 않는다.
- 보고서가 참조하는 `finance-mvp-erd.png`와 `finance-mvp-erd-details.png`는 현재 작업 폴더에 없다. 테이블 역할과 관계는 보고서 3절의 텍스트에서 확인할 수 있다.
- 인수인계 작성 시작 시 로컬 브랜치는 `master`였고, Git에 추적된 파일은 `README.md` 하나였다. 기획 보고서도 다음 커밋에 포함해야 다른 PC에서 열 수 있다.

## 설계에서 이어갈 결정

- AI가 자연어를 이해하고 추가 질문·조건 추출·설명을 담당한다. 사용자가 조건을 확인한 뒤 서버가 후보 필터링, 계산, 정렬을 수행한다. 입력이 부족하면 필요한 조건을 묻거나 비교의 한계를 표시한다.
- 상품군 안에서 같은 의미의 금리와 조건을 비교한다. 공시 금리·한도와 개인 심사 결과를 구분하고, 미공시 값은 결측으로 유지한다. 예상 이자·상환액에는 계산 가정과 확인되지 않은 비용을 표시한다.
- 공시 원문과 기준일·수집일을 보존한다. 상품군별 필드 차이를 매핑하고, 수집 실패와 미등재를 구분한다. 추천 실행에는 당시 입력·상품 조건·계산 가정을 남겨 조건 변경 전후를 비교할 수 있게 한다.
- 회원 공통 선호와 상담별 금융 입력을 구분한다. 필요한 정보만 수집하고 대화·추천 스냅샷도 접근 제어와 탈퇴 시 삭제 정책에 포함한다. 비밀번호 해시, 표시용 마스킹, 저장 보호는 각각 목적에 맞게 설계한다. API 키와 실제 이용자 데이터는 Git에 올리지 않는다.

## 다음 작업 제안

- 적금 흐름에 적용한 [설계 초안과 API 계약](../docs/적금_추천_설계_초안.md), [적금 추천 ERD](../docs/savings-recommendation-erd.svg)를 작성했다. 로그인 상담 및 추천 이력 복원은 초안의 가정이다. 적금 실응답으로 상품·옵션 식별 및 한도 의미를 검증한 뒤 저장 제약과 구현 범위를 확정한다.

설계 학습의 다음 단계는 적금 비교·재추천 사례로 아키텍처 초안을 그리는 것이다. “A은행은 다시 포함해줘” 요청에서 화면·서버·AI·저장소가 주고받는 정보를 적는다. 서버는 직전 확정 조건을 기준으로 A은행을 제외 목록에서 제거하고, 나머지 조건을 유지해 다시 검색한다. 화면에는 적용 조건과 결과를 표시한다. 새로고침이나 다음 날에도 상담을 복원할지는 미정이다. 적금은 설계 실습 사례다.

1. Finlife 실응답으로 상품군별 권역·페이지 수집, 상품·옵션 식별키, 결측·0의 의미, 중복 가능성을 확인한다. 특히 개인사업자대출 옵션의 식별 기준을 검증한다.
2. 검증 결과를 바탕으로 DB 타입·제약·인덱스와 기술 스택을 결정하고, 최초로 구현할 상품군과 흐름을 정한다.
3. 선택한 상품군에서 공시 수집 → 저장 → 목록·상세 조회 → 조건 기반 추천을 연결한다. 확인된 데이터와 계산 근거를 AI 설명에 전달하는 방식을 검증한다.

## 다른 PC에서 재개하기

1. GitHub 저장소를 처음 사용한다면 클론하고, 이미 클론했다면 작업 브랜치를 최신 상태로 맞춘다.
2. Codex에서 저장소 루트를 열고 “`handoff/Agent.md`를 읽고 현재 상태에서 이어서 진행해줘”라고 요청한다.
3. 작업을 마치면 완료한 내용, 검증 결과, 새 결정과 근거, 다음 작업 또는 막힌 점을 이 문서에 반영한다. 변경 파일과 문서를 함께 커밋하고 작업 브랜치를 푸시하면 다른 PC에서도 같은 상태를 확인할 수 있다.
